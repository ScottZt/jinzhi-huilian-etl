## 核心架构：分支隔离

```
本地工作目录 (quantsync-etl)
    │
    ├── main 分支（完整内容）
    │   ├── 核心引擎 + 前端 UI
    │   ├── backend/plugins/official_*.py（6 个付费插件源码）
    │   ├── scripts/pack_jspack.py（打包脚本）
    │   ├── pro-content/（内容包物料）
    │   │   ├── docs/（操作手册 + 25 个教程）
    │   │   ├── workflows-v1/（工作流 JSON 源）
    │   │   └── versions/（打包产物）
    │   ── dist/*.jspack（内容包）
    │
    │   git push 金汇智连 main  →  Gitee 私有仓库
    │
    └── open-source 分支（脱敏内容）
        ├── 核心引擎 + 前端 UI（与 main 共享）
        ├── backend/plugins/official.json（元数据，可保留）
        └── ❌ 不含 official_*.py、pack_jspack.py、pro-content/、dist/*.jspack
            git push origin open-source:main  →  GitHub 公开仓库
```

### 两个分支的区别

| 内容 | main（Gitee 私有） | open-source（GitHub 公开） |
|------|:---:|:---:|
| 核心引擎代码 | ✅ | ✅ |
| 前端 UI 代码 | ✅ | ✅ |
| 内容包导入机制（UI） | ✅ | ✅ |
| 版本徽章 / 购买指南 | ✅ | ✅ |
| License 公钥 | ✅ | ✅ |
| `official.json`（节点元数据） | ✅ | ✅ |
| **`official_*.py`（6 个付费插件源码）** | ✅ | ❌ |
| **`pack_jspack.py`（打包脚本）** | ✅ | ❌ |
| **`pro-content/` 整目录** | ✅ | ❌ |
| **`dist/*.jspack`（打包产物）** | ✅ | ❌ |

## 日常开发流程

### 在哪个分支开发？

**在 `main` 分支开发。**

```bash
cd D:/04.量化/quantsync-etl

# 确保在 main 分支
git checkout main
```

### 开发完成后提交

```bash
# 1. 查看变更
git status
git diff

# 2. 安全检查（见下方"安全检查"章节）

# 3. 提交到 main
git add -A
git commit -m "feat: 描述改动"

# 4. 同步到 open-source 分支
git checkout open-source
git merge main --no-edit

# 5. 在 open-source 上清理敏感内容
rm -f backend/plugins/official_*.py
rm -f scripts/pack_jspack.py
rm -rf pro-content/
rm -f dist/*.jspack

# 6. 提交 open-source 的清理
git add -A
git commit -m "chore: 同步 main 并清理敏感内容"

# 7. 推送
git push 金汇智连 main          # main → Gitee
git checkout main               # 切回 main
git push origin open-source:main # open-source → GitHub
```

### 简化版（无敏感内容变更时）

如果本次改动**没碰付费插件、打包脚本、pro-content/**，可以简化：

```bash
cd D:/04.量化/quantsync-etl
git checkout main

# 开发...

git add -A && git commit -m "feat: xxx"

# 同步两个分支
git checkout open-source && git merge main --no-edit
git checkout main

# 推送
git push 金汇智连 main
git push origin open-source:main
```

## 内容包发布

### 目录结构约定

```
pro-content/
├── docs/                     # 操作手册 + 25 个教程
├── workflows-v1/             # v1.0 工作流 JSON 源（25 个 .json）
├── workflows-v1.1/           # v1.1 增量补丁（v1.0 全部 + 新增）
├── versions/                 # 已打包产物（按版本号归档）
│   ├── 1.0/content.jspack    # 基础包
│   ── 1.1/content.jspack    # 增量补丁
```

**命名规则**：
- 小版本迭代（bug 修复、新增工作流）：`1.0 → 1.1 → 1.2` 作为**增量补丁**
- 大版本（架构变动、UI 重新设计）：`1.x → 2.0` 作为**新基础包**

### 首次发布基础包（v1.0）

```bash
cd D:/04.量化/quantsync-etl
git checkout main

# 1. 准备数据：把 25 个工作流的 JSON 放到 pro-content/workflows-v1/
#    （可从 docs/example_workflows.md 导出：python scripts/export_pro_workflows.py -o pro-content/workflows-v1）

# 2. 打包
python scripts/pack_jspack.py \
  --workflows-dir pro-content/workflows-v1 \
  --plugins-dir backend/plugins \
  --docs-dir pro-content/docs \
  -n "金智汇联专业版内容包" \
  --version "1.0" \
  -o pro-content/versions/1.0/content.jspack

# 3. 验证
python -c "
import zipfile, json
with zipfile.ZipFile('pro-content/versions/1.0/content.jspack') as zf:
    m = json.loads(zf.read('manifest.json').decode('utf-8'))
    print('workflows:', m['workflows_count'])
    print('plugins:', len(m['plugins']))
    print('docs:', m.get('docs_count', 0))
"

# 4. 提交（基础包是资产，要进 git）
git add pro-content/
git commit -m "release: pro content pack v1.0 (base, 25 workflows + 6 plugins + 25 docs)"
git push 金汇智连 main
```

### 后续发布增量补丁（v1.1 / v1.2 / ...）

当新增 N 个工作流（不动老工作流）：

```bash
cd D:/04.量化/quantsync-etl
git checkout main

# 1. 准备数据：复制前一版本目录 + 新增工作流 JSON
cp -r pro-content/workflows-v1.0 pro-content/workflows-v1.1
# 在 workflows-v1.1/ 里新增 N 个 .json

# 2. 打包（--patch 模式，自动跳过基础包已有的工作流）
python scripts/pack_jspack.py \
  --workflows-dir pro-content/workflows-v1.1 \
  --plugins-dir backend/plugins \
  --docs-dir pro-content/docs \
  -n "金智汇联专业版内容包 补丁 v1.1" \
  --version "1.1" \
  --patch --base-version "1.0" \
  -o pro-content/versions/1.1/content.jspack

# 3. 验证（补丁包应只含新增工作流）
python -c "
import zipfile, json
with zipfile.ZipFile('pro-content/versions/1.1/content.jspack') as zf:
    m = json.loads(zf.read('manifest.json').decode('utf-8'))
    print('is_patch:', m.get('is_patch'))
    print('base_version:', m.get('base_version'))
    print('workflows in patch:', m['workflows_count'])
"

# 4. 提交
git add pro-content/
git commit -m "release: pro content pack patch v1.1 (+N workflows)"
git push 金汇智连 main
```

### 大版本发布（v2.0）

大版本是**新基础包**，不再依赖 v1.x：

```bash
# 1. 准备 v2.0 数据（可能包含全新的工作流 + 新插件）
mkdir -p pro-content/workflows-v2.0
# 添加 v2.0 工作流 JSON

# 2. 打包（不加 --patch，作为新基础包）
python scripts/pack_jspack.py \
  --workflows-dir pro-content/workflows-v2.0 \
  --plugins-dir backend/plugins \
  -n "金智汇联专业版内容包 v2" \
  --version "2.0" \
  -o pro-content/versions/2.0/content.jspack

# 3. 提交
git add pro-content/
git commit -m "release: pro content pack v2.0 (base, major version)"
git push 金汇智连 main
```

### 分发给用户

**新用户**（第一次买）：
- 给最新的**基础包** + （如有补丁）**最新补丁**
- 例：v1.2 已发布，给 `versions/1.0/content.jspack` + `versions/1.2/content.jspack`

**老用户**（已买 v1.0，升级到 v1.1）：
- 只给**补丁包**
- 例：`versions/1.1/content.jspack`

**大版本升级**（v1.x → v2.0）：
- 作为**独立产品另售**，给新基础包 `versions/2.0/content.jspack`
- 销售文案：「v2.0 是新版本，需单独购买；已购 v1.x 用户不受影响」

**发送方式**：
- 知识星球：发文件到星球，会员自取
- 闲鱼：通过聊天 / 网盘发文件
- 微信：直接发文件

## 安全检查（每次推 open-source 前必做）

切到 `open-source` 后跑这个脚本：

```bash
cd D:/04.量化/quantsync-etl
git checkout open-source

echo "=== 安全检查 ==="

# 1. pro-content 不应该存在
echo -n "1. pro-content/: "
ls pro-content/ 2>/dev/null && echo "   [FAIL] 存在！" || echo "[PASS] 不存在"

# 2. 无私钥
echo -n "2. 私钥文件： "
find . -name "license_private_key.pem" -not -path "./.git/*" 2>/dev/null | grep -q . && echo "[FAIL] 发现！" || echo "[PASS] 无"

# 3. 无激活码生成函数
echo -n "3. 激活码生成： "
grep -r "def generate_activation_code" backend/app/ 2>/dev/null && echo "[FAIL] 发现！" || echo "[PASS] 无"

# 4. 无官方插件源码（这是付费资产）
echo -n "4. 官方插件源码： "
OFFICIAL_COUNT=$(find backend/plugins/ -name "official_*.py" 2>/dev/null | wc -l)
[ "$OFFICIAL_COUNT" -gt 0 ] && echo "[FAIL] 发现 $OFFICIAL_COUNT 个！" || echo "[PASS] 无"

# 5. 无打包脚本
echo -n "5. 打包脚本： "
ls scripts/pack_jspack.py scripts/export_pro_workflows.py 2>/dev/null && echo "[FAIL] 存在！" || echo "[PASS] 无"

# 6. 无打包产物
echo -n "6. 打包产物 dist/*.jspack: "
ls dist/*.jspack 2>/dev/null && echo "[FAIL] 存在！" || echo "[PASS] 无"

# 7. 无工作流 JSON 泄露（前端 example_workflows.js 中专业版不应含 workflow 字段）
echo -n "7. 前端工作流泄露： "
python -c "
import re, json
with open('backend/app/static/example_workflows.js', 'r', encoding='utf-8') as f:
    c = f.read()
m = re.search(r'window\.EXAMPLE_WORKFLOWS_DATA = (\{.+?\});', c, re.S)
if m:
    d = json.loads(m.group(1))
    leaked = [e['id'] for e in d['examples'] if 'workflow' in e and e['workflow']]
    print(f'[FAIL] 泄露 {len(leaked)} 个' if leaked else '[PASS] 无泄露')
else:
    print('[WARN] 未找到文件')
"

echo "=== 检查完成 ==="
git checkout main
```

如果有任何 `[FAIL]`，**不要 push**，先在 open-source 上删除/清理对应内容。

## 常见问题

### Q1：为什么 open-source 分支没有 pro-content？

pro-content 包含付费工作流 JSON 源 + 打包产物，属于**商业资产**。开源仓库只含工具本身，付费内容通过 Gitee 私有仓库存放 + 知识星球 / 闲鱼分发。

### Q2：打包时为什么跳过 base 已有的工作流？

增量补丁只发给已装基础包的老用户。他们已经有了 v1.0 的 25 个工作流，补丁包里再装一遍会覆盖用户可能的自定义修改。补丁只装**新增**的部分，老工作流保留原样。

### Q3：老用户升级要装几个包？

- 从 v1.0 → v1.1：只装 v1.1 补丁
- 从 v1.0 → v1.2：先装 v1.1 再装 v1.2（或装最新补丁 v1.2，因为它基于 v1.0 之上的全部状态）
- 从 v1.x → v2.0：装 v2.0 基础包（独立产品，需购买）

### Q4：大版本 v2.0 发布后，v1.x 用户怎么办？

- v1.x 用户继续使用 v1.x 的所有补丁（维护到停止更新）
- v2.0 作为新产品另售，用户自愿购买
- 销售文案明确写：「买断当前版本，大版本另售」

### Q5：为什么开源仓库还要保留 `backend/plugins/official.json`？

那是**元数据**（节点类型、显示名、分类），不含插件实现代码。前端 UI 用来渲染节点面板。付费资产是 `official_*.py` 里的 Python 实现，所以 open-source 只删 `official_*.py` 不删 `official.json`。

### Q6：打包产物要不要 commit 进 main？

**要。** 打包产物 `pro-content/versions/*/content.jspack` 是商业资产的历史归档，必须进 git。
- 可追溯每个版本的包内容
- 用户报 bug 时可以拉出对应版本的包复现
- 不会泄露给 GitHub（open-source 分支不含 pro-content）

### Q7：误把敏感内容推到 GitHub 怎么办？

1. 立即 `git push origin --delete main` 删除远端分支（如有可能）
2. 用 `git revert` 或 `git rebase -i` 清理本地 open-source 历史
3. 必要时重写历史 + force push（谨慎，会影响其他协作者）
4. 事后补安全检查到 CI

### Q8：我想添加新的官方插件，流程是什么？

1. 在 main 分支写 `backend/plugins/official_xxx.py`
2. 更新 `backend/plugins/official.json` 注册节点
3. 本地测试（重启后端验证节点能用）
4. commit 到 main
5. 同步到 open-source 时**删除** `official_xxx.py`（保留 `official.json`）
6. push
