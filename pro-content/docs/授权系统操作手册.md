## 1. 商业模型（方案 A）

### 1.1 核心设计

| 维度 | 设计 |
|---|---|
| **工具本体** | 开源 + 全功能开放。所有节点、数据源、调度、清洗、并发均无门槛。 |
| **付费内容** | 精选工作流模板 + 高级插件，打包成 `.jspack` 交付 |
| **付费方式** | 一次性买断**当前版本**；大版本更新（如 v2.0）作为独立产品另售 |
| **激活码** | **已废弃**。导入 `.jspack` 即自动显示专业版标识 |
| **分发渠道** | 知识星球（会员制） / 闲鱼（单次买断） |

### 1.2 销售文案要点

> **金智汇联 ETL · 专业版内容包**
>
> 当前版本（v1.0）一次性买断，含 25 个工作流 + 6 个高级插件。
>
> - 工具本体 100% 开源免费，无功能阉割
> - 专业版 = 生产级模板 + 高级插件（节省开发时间）
> - 买断当前版本，未来大版本作为独立产品另售

>
> 知识星球会员享受会员期内所有更新。

### 1.3 用户视角

1. **下载开源工具**：GitHub `ScottZt/jinzhi-huilian-etl`，全功能可用
2. **购买内容包**：知识星球 / 闲鱼，得到 `.jspack` 文件
3. **导入内容包**：UI 中「📦 导入内容包」上传 → 自动显示 👑 专业版标识 + 25 个工作流入库

### 2.5 判定逻辑

```python
# 后端 app/api/license.py
def get_license_info():
    info = dict(lm.get_license_info())
    installed = content_pack.get_installed_packs() or []
    info["installed_packs_count"] = len(installed)
    info["installed_pack_names"] = [p.get("name") for p in installed]
    info["edition"] = "pro" if installed else "open_source"
    return info
```

**关键点**：`edition` 只看 `_installed_packs` 元数据是否为空，与 License 无关。

## 3. 内容包导入流程

### 3.1 UI 入口

1. 顶栏徽章 → 「导入内容包」弹窗
2. 关于页 → 「📦 内容包导入」 → 「导入内容包」按钮
3. 导入示例弹窗 → 「📦 导入内容包」按钮

### 3.2 上传 .jspack 流程

```
[用户选择 .jspack 文件]
    │
    ▼
POST /api/content-packs/validate    ← 校验 manifest 格式 + 预览内容
    │
    ▼
[前端显示预览：包名 + 版本 + N 个工作流 + M 个插件]
    │
    ▼
[用户点「确认导入」]
    │
    ▼
POST /api/content-packs/import       ← 实际导入
    │
    ▼
后端 app/core/content_pack.py::import_pack()
    ├── 检查 is_patch：
    │     ├── False → 基础包：按 name 去重导入
    │     └── True  → 增量补丁：
    │                   ├── 检查 base_version 已装（否则拒绝）
    │                   └── 只导入 base 没有的工作流
    ├── 导入工作流到 workflows 表
    ├── 导入插件到 backend/plugins/
    ├── _save_pack_record() 写入 _installed_packs 元数据
    └── 返回导入结果
    │
    ▼
前端 loadLicenseInfo()
    ├── 拉 /api/license/info（edition 字段刷新）
    ├── 顶栏徽章从 🌱 切 👑
    └── 关于页版本号同步更新
```

### 3.3 增量补丁的特殊逻辑

| 包类型 | manifest.is_patch | 导入行为 |
|---|---|---|
| 基础包 | `false` 或缺失 | 按 name 去重，已存在的工作流跳过 |
| 增量补丁 | `true` | 1. 检查 base_version 已装（否则拒绝）<br>2. 只跳过 base 包内的工作流名<br>3. 允许新增工作流导入 |

补丁包 manifest 示例：

```json
{
  "pack_version": "1.0",
  "name": "金智汇联专业版内容包 补丁 v1.1",
  "pack_version_label": "1.1",
  "edition": "professional",
  "is_patch": true,
  "base_version": "1.0",
  "workflows_count": 3,
  "workflow_names": ["新增工作流 A", "新增工作流 B", "新增工作流 C"],
  "plugins": [...],
  "created_at": "2026-08-16",
  "description": "..."
}
```

### 3.4 卸载 / 重置

UI 暂未提供卸载按钮。如需重置为开源版：

```python
# 在 backend 目录运行
import sqlite3
from pathlib import Path

db_path = Path.home() / "AppData/Roaming/jinzhihuilian/jinzhihuilian.db"
conn = sqlite3.connect(db_path)
conn.execute("DELETE FROM metadata WHERE key='_installed_packs'")
conn.commit()
conn.close()
# 重启后端 → 顶栏徽章回到 🌱
```

> **注意**：这只会清掉元数据，**不会**删除已导入的工作流。工作流需要到「ETL 工作流」页面手动删除。

## 4. 数据结构

### 4.1 .jspack 文件格式

`.jspack` 本质是 ZIP 文件，包含：

```
my-pack.jspack (ZIP)
├── manifest.json         # 包元信息
├── workflows.json        # 工作流数组 [{name, description, workflow_json}, ...]
└── plugins/              # (可选) 插件 .py 文件
    ├── official_outlier.py
    ├── official_pattern.py
    └── ...
```

### 4.2 manifest.json 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `pack_version` | string | 包格式版本（当前 `"1.0"`） |
| `name` | string | 包名 |
| `pack_version_label` | string | 包版本号（如 `"1.0"` / `"1.1"`） |
| `edition` | string | `"professional"` |
| `workflows_count` | int | 工作流数量 |
| `workflow_names` | string[] | 工作流名列表（**增量补丁判定依赖此字段**） |
| `plugins` | string[] | 插件名列表 |
| `created_at` | string | 创建日期 |
| `description` | string | 包描述 |
| `is_patch` | bool | 是否为增量补丁 |
| `base_version` | string | 补丁依赖的基础包版本号（仅补丁包） |
| `skipped_by_base` | int | 打包时跳过的基础包工作流数（仅补丁包） |

### 4.3 已安装包元数据

位置：`%APPDATA%/jinzhihuilian/jinzhihuilian.db` 的 `metadata` 表，key = `_installed_packs`

值：JSON 数组，每个元素是安装过的包的 manifest：

```json
[
  {
    "pack_version": "1.0",
    "name": "金智汇联专业版内容包",
    "pack_version_label": "1.0",
    "edition": "professional",
    "is_patch": false,
    "workflows_count": 25,
    "workflow_names": ["TDX本地 → 写入DuckDB", ...],
    "plugins": ["official_outlier", "official_pattern", ...],
    "created_at": "2026-08-16",
    ...
  },
  {
    "pack_version": "1.0",
    "name": "金智汇联专业版内容包 补丁 v1.1",
    "pack_version_label": "1.1",
    "edition": "professional",
    "is_patch": true,
    "base_version": "1.0",
    "workflows_count": 3,
    "workflow_names": ["新增工作流 A", "新增工作流 B", "新增工作流 C"],
    ...
  }
]
```

### 4.4 后端 API

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/license/info` | GET | 返回 `edition` / `installed_packs_count` / `installed_pack_names` |
| `/api/content-packs/validate` | POST | 上传 `.jspack`，返回预览 |
| `/api/content-packs/import` | POST | 上传 `.jspack`，实际导入 |
| `/api/content-packs/status` | GET | 返回已安装包详情 |

> **注意**：`/api/license/activate` 和 `/api/license/deactivate` 接口虽仍存在于代码中，但前端 UI 已不再使用。方案 A 下激活码链路已废弃。

## 6. 激活码链路（已废弃）

### 6.1 历史

- 2026-08-16 之前：使用激活码 + 私钥签名（Ed25519）
- 2026-08-16（方案 A）：**激活码链路废弃**

### 6.2 废弃的内容

| 文件 / 字段 | 状态 |
|---|---|
| `pro-content/license/license_private_key.pem` | 已删除（commit 43af6f3） |
| `pro-content/license/gen_license.py` | 已删除 |
| `backend/app/core/license_manager.py::_verify_activation()` | 代码仍在但不再被调用 |
| `backend/app/static/index.html` 中的 `activateLicense()` | 已删除 |
| `manifest.json` 中的 `activation_code` 字段 | 已废弃 |

### 6.3 为什么保留公钥？

`backend/app/core/license_manager.py` 顶部仍有 `_PUBLIC_KEY_PEM` 和 `_verify_activation()` 函数。这是**兼容性保留**，以防未来想重新启用激活码。当前无任何代码路径会调用这些函数。

## 7. 常见问题

### Q1：顶栏显示 👑 专业版，但工作流列表里没有 25 个专业工作流？

**诊断**：元数据 `_installed_packs` 存在（所以显示 👑），但工作流可能导入失败。

```python
# 检查元数据
from app.core.content_pack import get_installed_packs
print(get_installed_packs())

# 检查工作流表
from app.persistence import sqlite_repo
print(len(sqlite_repo.list_workflows()))
```

可能原因：
- 之前导入时部分工作流失败（看后端日志）
- 手动删除了工作流但没清元数据

### Q2：用户导入补丁包报错「导入补丁前需先安装基础包」？

用户需要先导入对应的基础包（`base_version` 指向的版本）。

分发补丁包时，确认用户已装基础包。如果用户是新用户，**不要只给补丁**，要给基础包（或基础包 + 补丁组合）。

### Q3：为什么导入示例里还有「🔒 专业版」卡片（在旧版本里）？

旧版本的 `content-registry.js` 把 25 个文档示例硬编码为 `tier: "pro"`，并在 UI 里显示锁定样式。新版本已改成「目录 + 状态」：
- 已装包：显示 ✅「已导入 · 在工作流列表使用」
- 未装包：显示 📦「尚未导入内容包」占位

如果用户看到旧样式，请升级到最新代码。

### Q4：用户反馈「点击徽标弹出文件选择框」？

**Bug**：`openModal` 自动 focus 第一个 input，file input 的 click 会触发系统文件选择框。

**修复**（已合入）：`openModal` 选择器加了 `:not([type="file"])`。如果用户仍遇到，请强刷浏览器 `Ctrl+F5`。

### Q5：前端上传 .jspack 报「鉴权失败」？

**原因**：旧代码用原生 `fetch()` 发 FormData 时没带 `X-API-Key`。

**修复**（已合入）：`api()` 函数支持 FormData（自动跳过 `Content-Type: application/json` 并带上 `X-API-Key`）。`previewContentPack` / `importContentPack` 已改用 `api()`。

### Q6：`/api/license/info` 返回 `edition: "pro"` 但我没导入过东西？

可能原因：
- 数据库里残留 `_installed_packs` 元数据（之前测试导入的）
- 重置：见 §3.4 卸载/重置

### Q7：开源仓库为什么也有 `official.json`？

`official.json` 只是节点元数据（类型、显示名、分类），用于前端渲染节点面板。付费资产是 `official_*.py` 里的实现代码。

所以：
- open-source 分支：保留 `official.json`（元数据），删除 `official_*.py`（实现）
- main 分支：两者都有

### Q8：如何判断用户是 v1.0 还是 v1.1？

查 `_installed_packs` 元数据：

```json
[
  {"pack_version_label": "1.0", "is_patch": false, ...},
  {"pack_version_label": "1.1", "is_patch": true, "base_version": "1.0", ...}
]
```

- 只有 `1.0` → 基础包用户
- `1.0` + `1.1` → 已升级到 v1.1
- `1.0` + `1.1` + `1.2` → 已升级到 v1.2

### Q9：为什么用增量补丁而不是全量覆盖包？

全量覆盖包（v2 含全部 30 个工作流）也能工作，但有两个问题：
1. **用户自定义修改被覆盖**：如果用户在导入后修改了 v1.0 的某个工作流，覆盖导入会覆盖掉用户的修改
2. **带宽浪费**：老用户每次都要重新下载 25 个已存在的工作流

增量补丁只含新增工作流，既省带宽又保护用户自定义。

### Q10：我想从 v1.0 直接升级到 v1.2，可以跳过 v1.1 吗？

**可以。** v1.2 补丁的 `base_version` 字段应填它实际基于的版本：

- 如果 v1.2 是基于 v1.0 的累积补丁 → `base_version: "1.0"`，可直接从 v1.0 升级
- 如果 v1.2 是基于 v1.1 的增量补丁 → `base_version: "1.1"`，必须先装 v1.1

**建议**：每个新版本都基于「前一版本的全部状态」打包，这样 `base_version` 总是填前一个版本号，用户可以一路累积升级。
